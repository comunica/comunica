Skipping service descriptions (issue 13)

You were right: skipping the service description of every forced SPARQL source also drops its VoID description, its sd: features (extension functions, accepted methods, default graph) and the VoID-based estimates, so it is not the right fix in general. I kept it out of the PRs.

On this workload, though, the service descriptions contribute nothing: of the 54 endpoints, none serves VoID, only 7 serve any sd: triples, the 32 ldmax endpoints redirect to the site's schema.org catalogue page (99 KB, 780 quads, per source and per query), and TriplyDB answers with JSON or a 400. The cost is mostly latency: the first query request waits 1.3 to 3.8 s, and up to 3 MB are fetched for 35 sources.

The clean alternative keeps the service description but takes it off the critical path: identify a forced SPARQL source immediately, merge the service description into the source when it arrives, and only wait for it (with the existing 3 s timeout) where its content is used, such as VoID estimates. In addition, an endpoint whose response had no sd: or void: triples can be remembered for the lifetime of the engine, so later queries skip it. Not implemented yet; it touches how QuerySourceSparql receives its metadata.

Clean solutions, implemented

All on claude/nde-fed-clean, configurable through actor parameters with defaults, no environment switches.

OPTIONAL over multiple sources as planned VALUES joins per block

Issue 6
CleanUnit tests: 100%Run the benchmarks before a PR
Design
New actor actor-rdf-join-optional-bind-block. It slices the left side into blocks of up to 64 distinct key values, joins each block with the right side as Join(VALUES, right) (or Filter(Join(...), expr) for OPTIONAL with FILTER) through the normal planner, and adds the left bindings without results. Each VALUES row carries a row number, so results are matched to the row that produced them, even when a row with unbound values produces results that agree with another row.
Why clean
It is its own actor that competes on coefficients, only for right sides without a single source (those stay with optional-bind-source). A VALUES join is plain SPARQL join semantics, so it needs none of the bind-safety restrictions, and it streams per block instead of materializing the whole left side like the prototype.
Measured
Q4: failed (baseline) to 2,026 correct distinct rows in 130 s. Q6: 600 s timeout to 391 correct distinct rows in 34.8 s.
Open
Every block still goes to all 34 sources (3,036 of Q4's 6,030 requests), and a block of 64 keys becomes 3 VALUES requests per source, as the bind-source join splits it into blocks of 25. Aligning the two block sizes and pruning sources by value space would cut that. The prototype was faster on Q4 (87 s); run-to-run endpoint variation is large, so this needs repeated runs to judge.

Share identical in-flight requests of a query

Issue 5
CleanHelper tests: 100%Integration tests missing
Design
SparqlRequestSharing in the SPARQL source. Identical SELECT and COUNT requests of the same query (scoped by its queryTimestamp) share one request while it is in flight. Bindings are read as they arrive into a buffer of at most 1,000 bindings (new parameter shareRequestsMaxBindings), so a consumer never waits for another one. Nothing is kept after a request completes.
Why not the prototype
The prototype made later consumers wait until the first one had read everything, which can deadlock when both streams feed the same join, and it kept results for the lifetime of the source, which with source reuse (#1992) spans queries and can serve stale data.
Measured
Q3: 115 duplicate requests to 1, total 268 to 156 requests. All 115 duplicates were concurrent (about 20 ms apart), which is why #1983 (reuse after completion) does not catch them.
Open
Integration tests in QuerySourceSparql-test. ASK requests are not shared yet.

Continue results that may be capped with OFFSET pages

Issue 3
CleanUnit tests missingRelies on stable order
Design
If a response has a multiple of 1,000 rows (new parameter resultPageMultiple), the SPARQL source requests OFFSET n LIMIT n pages until a page is shorter. A false positive costs one request without results. Original query strings and operations with their own slice are not paged.
Evidence
TriplyDB gives no signal: LIMIT 20000 returns exactly 10,000 rows, with no header or response field. Exact COUNTs cannot be the signal either, because the capped Q1 operation is a 4-pattern BGP whose cardinality is only a local estimate. Ordered paging is impossible there: the endpoint refuses ORDER BY with OFFSET 10000 LIMIT 10000 with "Virtuoso 22023 Error SR353: Sorted TOP clause specifies more then 20000 rows to sort. Only 10000 are allowed".
Measured
Q1: 12 of 334 rows to all 334.
Open
Unit tests. Unordered pages assume the endpoint evaluates the same query in the same order, which held on TriplyDB but is not guaranteed by SPARQL.

Limit concurrent requests per host once it signals overload

Issue 11
CleanUnit tests: 100%Not exercised by a real overload yet
Design
New HTTP actor actor-http-limit-concurrency in the default config. No limit (up to maxLimit, 10,000) until a host answers 429 or 503 or a connection is lost. The limit then becomes half the requests in flight (once per burst) and grows by one per limit's worth of successes. A slot is released at the response headers, not at the end of the body, since holding slots for unread bodies can deadlock joins.
Evidence
The ldmax gateway (31 endpoints on one host) scales with concurrency: Q4b took 373 s with a cap of 64, 45 s with slow start from 16 to 1,024, 42 s from 64 to 4,096, and 35 s unlimited (peak 1,911 in flight). So any limit before overload is harmful there. Unlimited is not always safe either: baseline Q4 failed when one request was cut after 31 s with 1,745 requests in flight.
Measured
In the final run no host signalled overload (no 429, 503 or lost connection), so the limiter never engaged; ldmax peaked at 1,952 in flight. The RCE 503 bursts from earlier days did not recur.
Open
A test against a real or simulated overloading endpoint. The planner-side cause, thousands of concurrent bind-join requests, is untouched.

Retry lost connections by default

Issue 12, follow-up to #2034
CleanUnit tests missing
Design
Without a configured retry count, ActorHttpRetry now also retries requests that lost their connection (ECONNRESET, EPIPE, undici socket and closed errors, HTTP/2 GOAWAY, found by walking error.cause), only for replayable query requests. Refused connections and unknown hosts still fail immediately, so dead links do not get slower.
Evidence
genealogieonline.nl sends HTTP/2 GOAWAY frames; that made baseline Q2 fail, and one Q3 run. A GOAWAY means the request was not processed, so sending it again is safe.
Measured
Q2: failed to 53 correct rows in 30.5 s.
Open
Unit tests, and a decision whether it goes into #2034 or a follow-up PR.

Designs and decisions without code

Blank-node joins across sources (Q5, Q5b, Q7 still wrong)

Issue 4
Design only
Recommendation
An optimizer rewrite instead of the prototype's runtime re-anchoring: Join(A@S, Union(B@S, B@T)) becomes Union(Join(A, B)@S, Join(A@S, B@T)). This is exact by distributivity, keeps S's blank nodes inside S, and loses nothing, since blank nodes from S can never match T. It also turns the S part into one source query.
Why not re-anchoring
It needs a public way to get a blank node's source (today only the internal bc_<sourceId>_ label and a duck-typed sourceId), and every bind join and optional join would need it.

Join order without value-space knowledge (Q1: 291 MB)

Issue 10
Design only
Finding
Of Q1's 291 MB, about 180 MB are about 100 pages of RKD's own schema:sameAs triples (about 1M rows), and 107 MB are full scans of schema:creator on ldmax. RKD's sameAs links can never join with museum agents, but the planner cannot know that. Paging made this visible; before, the cap hid it by returning wrong results cheaply.
Recommendation
Value-space knowledge per source. VoID is not the way here: none of the 54 endpoints serves VoID. The NDE Dataset Knowledge Graph linksets are the realistic source.

Batch COUNT queries per source

Issue 14
Design only
Recommendation
Generalize the ASK batcher of #2010 into a batcher for single-row queries, with at most 16 per batch. On a batch timeout, give the slow entries infinite estimates or resend them alone, since one slow COUNT otherwise delays its whole batch. Prototype: Q2 63 to 9 COUNT requests, Q1 176 to 22.

Prefix pruning, transfer-cost metadata, multi-bind deferral

Issues 8 and 9
Dropped for now
Why
Prefix ASKs took 2.5 to 9 s on ldmax and slowed queries where nothing could be pruned, and no endpoint publishes void:uriSpace. Transfer-cost metadata was not decisive (the decisive changes were #2032 and #2033), and the multi-bind deferral only fixed a case that the transfer-cost prototype itself caused.
